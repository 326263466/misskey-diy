# 商品、订单与支付

`product`、`order`、`payment` 是独立的业务模块。`shop` 是集市入口和流程组合层，不拥有另一套商品或订单存储。管理员与普通用户使用相同发布接口和商品表。

## 模块边界

| 模块 | 负责的数据和行为 | 对外接口 |
| --- | --- | --- |
| ProductModule | 商品资料、发布权限、库存、版本冲突 | `products/create`、`products/update`、`products/mine` |
| OrderModule | 订单、累计购买量、订单号、CDK、成交快照 | `orders/list`、`orders/show` |
| PaymentModule | 支付配置、积分结算、平台账户和平台流水 | `payments/settings`、管理员支付设置 |
| ShopModule | 商品展示查询和购买流程编排 | `products/list`、`products/show`、`orders/purchase` |

商品和订单不直接读取对方的表，也不引用签到业务。CatalogService 汇总展示所需的商品、购买额度与余额；CheckoutService 编排购买。PaymentService 是积分钱包的唯一对接处，订单只保存支付凭证引用。

当前采用同库事务：先按统一顺序锁买卖双方账户，再锁商品，最后锁平台账户；限购、库存、订单、卖家收入和平台收入一起提交或回滚。以后拆成远程服务时，需要在支付边界引入持久化事件、幂等消费和补偿流程，不能把这些调用直接改成 HTTP 后仍假定数据库事务有效。

## 商品与订单

- 支持实物、虚拟商品。发布人只能管理自己的商品；平台设置由管理员管理。
- `perUserLimit = 0` 表示不限累计购买量，正数表示每位用户累计可购买的数量。一单多件与分次购买使用同一额度。
- 每单仍受整数范围、库存和可支付总额约束；界面显示实际可购买数量。
- 发布与购买都保存客户端请求键。相同请求可安全重试，更改请求内容不能复用同一键。
- 公开商品数据不含私密交付说明；订单、CDK 和交付内容仅买卖双方可读。
- 商品、订单与支付配置各有管理页，展示页不放管理入口。

## 编号和兑换码

订单号是 19 位数字字符串，由 PostgreSQL 持久序列分配，主键约束兜底，序列禁止循环。SQL 将 bigint 显式转换为文本，避免 JavaScript 大整数精度损失。编号不作为访问凭证，订单查询仍校验当前用户归属。

CDK 为 20 位大写 Base32 字符，使用密码学随机源生成，提供 100 位随机强度。界面按四组、每组五位展示，例如 `XXXXX-XXXXX-XXXXX-XXXXX`。数据库保存无分隔符形式并设置唯一约束，碰撞时重新生成；每笔订单一个 CDK 对应整单数量。

长度参考：[Shopify Gift Card 文档](https://shopify.dev/docs/api/admin-rest/latest/resources/gift-card)接受 8～20 位字母数字兑换码。本系统取 20 位，并排除容易混淆的部分字母。订单号采用常见的 64 位数字标识长度，但由数据库分配，不引入时钟回拨或重复工作节点编号的风险。

## 平台抽成

默认费率为 15%，以基点保存：`feeRateBps = 1500`。管理员可设为 0～10000 基点。手续费按订单总额计算，在最小单位 0.01 积分上向上取整，避免通过拆分小额订单规避手续费。

买家付款 = 卖家实收 + 平台收入。平台收入进入独立账户，并写入以业务凭证去重的平台流水；不会再次创建积分。订单保存成交时的费率、费用和实收，调整费率不改历史订单。

15% 抽成不是价格稳定保证。平台收入若重新发放，总积分仍然守恒；长期购买力还取决于新增奖励、积分回收、活跃用户和商品供给。发行与回收政策应另外制定，不由商品交易隐式修改。

## 迁移

一次性迁移将旧商品和订单搬入统一表，并删除旧 Meta 商品配置和钱包内的订单内容。原补签卡商品保留资料并下架，不再自动发卡。历史订单不补造未发生的卖家收入或抽成，没有结算资料时费用字段为空。

迁移不会改变历史钱包余额。缺少有效管理员时，旧商品保留但下架。存在业务数据时，回滚会拒绝删除新模型；只有空库可回滚结构。运行时代码不保留旧接口、旧服务别名或旧业务分支。
