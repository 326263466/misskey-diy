# 屏蔽与拉黑规范

新增或修改用户间社交内容、互动或提醒时参照本规范。屏蔽与拉黑是个人社交控制，不是全站业务授权。

## 原则

只保留现有两种关系，不新增设置或反向静音：

- 屏蔽（`mute`）：过滤 A 日常看到的 B 的动态、评论、群聊发言和社交提醒；B 仍能查看 A 的内容、发起原本允许的操作。A 主动访问 B 的主页、帖子详情或私信历史时不因屏蔽而失去访问权限。
- 拉黑（`block`）：任一方拉黑另一方，双方的社交内容互相不可见，不能再关注、私信或发起社交互动。不以此删除历史、撤销群成员资格、剥夺资源权限或中断订单履约。

不同产品对共同群聊和历史记录的处理并不完全一致，本文明确本项目的功能约定，不将它表述为统一的行业协议。

## 用词

| 功能 | 界面用词 | 代码 |
| --- | --- | --- |
| 阻止双方社交接触 | 拉黑、黑名单 | block / blocking |
| 只是自己不看，不限制对方查看自己 | 屏蔽 | mute |
| 隐藏服务器、关键词、Emoji、群消息 | 屏蔽 | instance block、word mute 等 |

账号相关 i18n 的 `mute` / `unmute` 统一写"屏蔽" / "取消屏蔽"，`block` / `unblock` 写"拉黑" / "取消拉黑"。音视频的静音保持原意，群聊只关提醒的功能使用"免打扰"，不得套用账号屏蔽文案。

## 一、建立拉黑时

`UserBlockingService.block()` 负责：双方互相取消关注和关注申请，把 B 移出 A 的社交列表，更新关系缓存后向远程发送 Block。取消拉黑不自动恢复关注。

既有私信、订单、资金流水保留，原当事人仍可按原权限查看、撤回和处理退款；拉黑不是删除证据的手段。历史私信可以查看和搜索，但不可通过编辑、回复或回应继续接触对方。

## 二、互动：双向禁止

以下操作只要存在拉黑关系就拒绝，不论哪一方发起：

| 类别 | 操作 |
| --- | --- |
| 关系 | 关注、关注申请、邀请入群、申请或直接加入对方的群 |
| 帖子 | 回复、转发、引用、回应、点赞、投票 |
| 聊天 | 私信、回应对方的消息、状态自动回复 |
| 定向赠与 | 新发起转账、打赏、指定红包及新的红包领取；已接受转账、已领取资金和退款仍按资金模块规则处理 |
| 文章 | 评论、回复评论、点赞评论 |

- 判断统一用 `UserBlockingService.isBlockedEither(a, b)`；事务内用 `manager.existsBy(MiBlocking, [{ blockerId: a, blockeeId: b }, { blockerId: b, blockeeId: a }])`。
- 撤销类操作（取消回应、取消点赞、删除自己的内容）不受限制，拉黑后仍能清理旧痕迹。
- 幂等重试返回既有结果，不因之后建立的拉黑而失败。

## 三、提醒：双向不产生

拉黑关系中的一方不会因另一方新发起的社交行为收到提醒、实时消息或社交 webhook，包括提及。群管理事件和必须送达的业务通知不能按普通个人发言过滤。

- `NotificationService` 在创建通知时统一过滤，新增通知类型无需重复判断。
- 不经过 `NotificationService` 的事件（如 `publishMainStream` 的 `mention` / `reply` / `renote`、webhook）由调用方用 `isBlockedEither` 跳过。
- 提及列表（`notes/mentions`）等同提醒，也排除拉黑关系中的对方。

## 四、内容可见性

| 场景 | 规则 | 实现 |
| --- | --- | --- |
| 动态、搜索、个人主页动态、实时推送、帖子详情和评论区 | 拉黑双向隐藏；引用和回复中的对方社交内容同样不可见 | `generateBlockedUserQueryForNotes`、`CacheService.getBlockedUserIds`、`NoteEntityService` |
| 用户资料 | 保留账号身份、公开简介及取消拉黑入口；不显示置顶帖子和动态 | `UserEntityService`、个人主页 |
| 文章及其评论 | 双向：互相按不存在处理 | `canReadArticle`、`ArticleService.commentsQuery` |
| 历史私信 | 原当事人仍可查看和搜索，不能借此新发消息、编辑或互动；自己的撤回操作仍可用 | `ChatService`、私信接口 |
| 共同群聊 | 屏蔽仅自己隐藏对方的普通发言；拉黑双方互相隐藏。时间线、搜索、引用和实时推送一致。不退群、不撤销管理权限，系统事件仍可见 | `ChatService`、`ChatEntityService`、聊天流 |
| 普通页面、图库、Play、收藏夹 | 不按账号屏蔽或拉黑剥夺资源访问权限，沿用各模块规则；收藏夹内的帖子仍遵守社交内容可见性 | 各资源服务和接口 |
| 集市商品、购买、订单履约、资金凭证 | 独立业务权限，不以屏蔽或拉黑隐藏商品、拒绝购买、取消订单或阻止既有资金结算 | 商品、订单、支付和钱包模块 |
| 转账、打赏和红包 | 新的定向赠与受拉黑限制以防骚扰；历史账目、已获得的资金和退款不受社交展示过滤影响 | `TransferService`、`TipService`、`RedPacketService` |

社交内容不可见时按"不存在"返回（如 `NO_SUCH_NOTE`），不暴露拉黑方向。帖子互动沿用 `YOU_HAVE_BEEN_BLOCKED` 错误码，前端统一显示"你们之间存在拉黑关系"。不能因此对商品返回 `NoSuchProductError`。

`userBlockingCache` 和 `userBlockedCache` 保留各自方向，内容入口通过 `getBlockedUserIds` 合并，不能将方向性缓存本身改成双向。SQL 过滤放在分页之前，嵌套引用在公共打包层处理。公开内容的匿名访问、其他账号访问，以及远端已收到的副本不受当前账号关系控制，不承诺撤回这些内容。

## 五、新增功能检查

1. 是否产生新的社交接触或定向赠与？是则按第二、三节检查拉黑，不将屏蔽升级为权限拒绝。
2. 是否展示社交内容？按第四节检查详情、列表、引用和实时推送；公开资源、历史私信和业务凭证不得套用社交内容过滤。
3. 后端拒绝时，前端是否给出可读提示，而不是通用的"出错了"？
4. 在已有的拉黑测试（`test/e2e/block.ts` 或对应模块的 unit 测试）中覆盖双向场景。

不要将社交屏蔽扩展成全站封锁；业务模块需要限制交易时，应定义自己的权限、封禁或风控规则。
